# 设置系统统一实施说明（2026-04-21）

## 1. 这份说明解决什么问题

当前设置系统已经不是单点问题，而是整体缺少统一约束。

表面现象包括：

- 设置页内外出现了两套灰度和多套表面层级
- 同类按钮、输入、下拉、开关、路径选择没有统一口径
- 右侧设置内容的排布方式混杂，有的像表单、有的像菜单、有的像说明页
- 某些页面沿用了一次性做法，没有回收到共享结构里
- `Readwise Reader` 等内容块已经形成明显特例，和其他设置页不是同一种语言

这会导致两个直接后果：

- 每新增一页设置，都要重新决定“长什么样”
- 当前页面即使局部修好，整体仍会继续发散

所以这次目标不是“修某一页”，而是把设置系统收回统一设计和统一结构。

## 2. 本次明确结论

### 2.1 灰度系统

设置系统不再保留“页外一套、页内一套”的长期分叉。

正式方向是：

- 使用一套统一的中性灰体系
- 设置页只允许在统一灰体系里使用少量明确角色
- 不再继续新增“某页专用灰”“某块专用灰”

设置页内部允许保留的灰度角色应压缩为：

- 主表面
- 侧栏表面
- 选中态表面
- 分隔线
- 边框

若某个颜色角色无法明确归入这几类，就不应继续存在。

### 2.2 设置页结构

设置页右侧内容统一收口为三层：

1. 页面标题区
2. 分组块
3. 分组内行项目

不再允许页面直接堆散乱控件，也不再允许某页把正文、操作、说明、跳转混成一整块。

### 2.3 行项目结构

设置行统一采用固定结构：

- 左侧：标题 + 说明
- 右侧：控件或动作

允许的差异只体现在控件类型，不体现在整行骨架。

### 2.4 控件分类

设置区正式只保留少数几类标准控件：

- 开关类
- 单选 / 下拉类
- 文本输入类
- 路径 / 文件夹选择类
- 危险操作类
- 说明 / 跳转类

今后新增设置项时，必须先归类，再落到对应样式；不能每页重新发明一套。

### 2.5 特例页面处理

`Readwise Reader` 这一类内容较多、流程较长的页面，可以在内容上复杂，但不能在外观和骨架上继续特例化。

必须统一的部分包括：

- 页面壳
- 分组结构
- 行项目骨架
- 标题与说明层级
- 按钮与次级操作样式

可以保留差异的部分仅限：

- 业务字段本身
- 业务流程说明
- 少量必要的状态反馈

## 3. 统一后的设置系统组成

### 3.1 页面壳

页面壳负责：

- 弹窗整体外观
- 左右栏布局
- 标题区
- 表面层级
- 分隔关系

页面壳不负责承载业务特例。

### 3.2 分组块

每个分组块只表达一个主题，例如：

- 阅读显示
- 导入行为
- 数据来源
- 同步与连接
- 危险操作

禁止把多个主题堆到同一组里，也禁止用“长页面 + 零散标题”代替分组。

### 3.3 行项目

行项目是设置系统的最小稳定单位。

每一行只允许承载一种主要交互：

- 开关
- 选择
- 输入
- 路径
- 跳转
- 操作

一行里若同时出现多个主交互，应优先拆行，而不是把它继续做成局部特例。

### 3.4 特殊说明区

当某类设置需要较长说明、状态回执或引导文字时，应落在统一的说明区样式里，而不是临时拼一块内容。

## 4. 本次不做什么

这份实施说明明确不追求一次性重写整个设置系统。

本次不做：

- 不把所有设置页一次性整体重排
- 不顺手改 unrelated 功能逻辑
- 不把“统一视觉”扩展成整仓所有页面的大改版
- 不在没有分类规则前先批量重做页面

原则是先定统一规则，再按优先级逐页收口。

## 5. 建议实施顺序

### Task 1：收口设置页基础 token

先处理最底层统一问题：

- 灰度角色
- 边框角色
- 分隔线角色
- 阴影角色
- 选中态角色

要求：

- 设置页不再继续持有额外私有灰度
- 当前已有 settings token 若与主体系重复，应合并或重命名
- 颜色角色必须清楚表达用途，而不是表达“某一页的局部长相”

### Task 2：定设置页共享结构

把设置页收成统一的共享结构：

- 页面壳
- 分组块
- 行项目
- 控件槽
- 说明区

要求：

- 共享结构必须能覆盖大多数设置页
- feature 页面只负责填内容，不再自定骨架

### Task 3：定控件分类与映射

为设置区建立明确映射：

- 哪些设置属于开关类
- 哪些属于选择类
- 哪些属于路径类
- 哪些属于危险操作类
- 哪些属于说明 / 跳转类

要求：

- 同类控件样式一致
- 同类交互位置一致
- 同类说明写法一致

### Task 4：以 `Readwise Reader` 作为首个收口样板

选择当前最不统一、最容易漂移的一页作为样板先收。

推荐先做 `Readwise Reader`，原因是：

- 它当前特例感最强
- 内容复杂，能提前验证共享结构是否够用
- 一旦它能回到统一体系，其他设置页更容易跟进

### Task 5：按优先级逐页清理剩余设置页

推荐顺序：

1. `Readwise Reader`
2. `Library`
3. `Import`
4. `Review`
5. `Backups`
6. 其他说明型页面

每次只收一页，不混做多页。

## 6. 验收口径

完成统一后，至少应满足这些结果：

- 用户能明显感受到所有设置页属于同一套系统
- 同类按钮、输入、下拉、开关在各页不再跳风格
- 页面不再出现“这页像表单、那页像说明书、另一页像临时菜单”的割裂感
- `Readwise Reader` 不再是设置系统里的例外壳层
- 新增设置项时，可以先分类再落位，而不是重想一遍页面结构

## 7. 当前建议

下一步最小可执行任务建议为：

- 先做 Task 1 + Task 2 的最小闭环
- 不立即大面积改页
- 完成后，立刻拿 `Readwise Reader` 做第一块样板收口

这样可以先把“统一规则”钉住，再进入逐页改造，避免再次出现“边做边长出新例外”。
